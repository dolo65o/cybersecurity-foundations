## ISO/IEC 19249 — Security Principles

### 5 Architectural Principles

| Principle | Core Idea | Example |
|-----------|-----------|---------|
| **Domain Separation** | Group related components into isolated domains with shared security attributes | x86 ring 0 (kernel) vs ring 3 (user apps) |
| **Layering** | Structure system into abstract levels; enforce security at each layer | OSI model — security policy per layer; relates to Defence-in-Depth |
| **Encapsulation** | Hide internals; expose only controlled interfaces | OOP: `increment()` method instead of direct variable access; APIs over direct DB access |
| **Redundancy** | Duplicate critical components for availability and integrity | Dual power supplies; RAID 5 — survives one drive failure + detects data corruption via parity |
| **Virtualization** | Share hardware across multiple OS instances; creates security boundaries | Cloud sandboxing; safe malware detonation environments |

---

### 5 Design Principles

| # | Principle | Core Idea | Example |
|---|-----------|-----------|---------|
| 1 | **Least Privilege** | Grant minimum permissions needed for a task — nothing more | Read-only access for users who only need to view documents |
| 2 | **Attack Surface Minimisation** | Reduce exposure by removing unnecessary services/features | Disable unused services on Linux hardening |
| 3 | **Centralized Parameter Validation** | Validate all input in one place — not scattered across codebase | Single validation library handles all user input; prevents SQLi, RCE, DoS |
| 4 | **Centralized General Security Services** | Consolidate security functions into shared services | Central authentication server (with redundancy to avoid single point of failure) |
| 5 | **Preparing for Error & Exception Handling** | Design systems to fail safe; don't leak info in error messages | Firewall crash → block all traffic (not allow all); DB errors → generic message, not stack trace |
